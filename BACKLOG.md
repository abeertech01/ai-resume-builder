## Existing Problems

1. ✅ **Upgrading can charge twice.** When a Premium user buys Premium Plus, checkout starts a second subscription instead of changing the existing one, so they would pay for both. Deleting the account would also cancel only one of them. (Seen in the code, not tested with Stripe.)
2. ✅ **The Billing page says "Your subscription will be cancelled on…" for everyone.** It shows whenever there is a renewal date, not only when a cancellation is scheduled. (Confirmed: the subscription in the database is not set to cancel.)
3. ✅ **The color picker opens behind the premium modal.** A free user who clicks "Change resume color" gets the modal and the color picker at the same time. Confirmed by tracing Radix's `PopoverTrigger`: it composes its own open/close toggle after our click handler and runs it regardless, unless `event.preventDefault()` is called. It wasn't, so the popover always force-opened — invisibly, behind the modal's overlay, which is why it wasn't visible just by looking. Fixed in `ColorPicker.tsx` by calling `event.preventDefault()` when the user isn't eligible.
4. ✅ **Logged-out visitors get an error on "Get Premium" / "Get Premium Plus".** Checkout needs an account, so the modal shows "Something went wrong". (Confirmed in the browser.) Fixed: the `(main)` layout now passes `isLoggedIn={!!session}` to `PremiumModal`, and when logged out, both buttons link to `/sign-up?from=editor` instead of calling checkout.
5. ✅ **The user's password hash is sent to the browser.** The layout gives the whole user record, including `passwordHash`, to the navbar, which runs in the browser. Only their own hash, but it should not be there. (Seen in the code: `(main)/layout.tsx` → `Navbar`.) Fixed: `(main)/layout.tsx` now builds a plain `{ firstName, lastName, email }` object for the `Navbar` prop instead of passing `session.user` through. `Navbar`'s `Pick<User, ...>` prop type never removed the extra fields at runtime — only the type checker saw a narrower shape; the actual object serialized to the browser was the full row.
6. ✅ **Emails are not lowercased.** "Foo@x.com" and "foo@x.com" can become two different accounts. (Seen in the code.) Fixed: `signUpSchema` and `logInSchema` (`lib/validation.ts`) now share one `emailField` that lowercases as part of parsing, so sign-up, login, and the login rate-limit key all agree on casing. Checked the live database first: all 8 existing accounts already had lowercase emails and none would collide after lowercasing, so no data migration was needed.
7. ✅ **The redirect after login is ignored.** Logged-out users are sent to `/sign-in?redirect=<page>`, but nothing reads it, so after logging in they always land on `/resumes`. (Seen in the code.) Fixed: `/sign-in` now reads `?redirect=`, passes it through `SignInForm` into the `logIn` action, which sends the user there on success. The action validates it's a same-site path first (must start with `/`, not `//` or `/\`) — otherwise this would be an open redirect, since the query param is attacker-controllable.
8. **Decide what to do with `emailVerified`.** The `User.emailVerified` field is unused as of now: nothing reads or writes it. (Seen in the code.)
